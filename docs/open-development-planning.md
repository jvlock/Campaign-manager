## Modes and isolation

| Server mode | Entry requirements | Planning | Operations |
|---|---|---|---|
| `restricted` | Default; trusted server-side identity verification and scoped grants needed for access. An absent verifier fails closed. | Only explicitly authorized scoped routes; no open-development records. | No live execution authorized by this phase. |
| `open-development` | Explicit server configuration, `NODE_ENV=development`, non-deployment environment and successful private database isolation check **before listening or serving planning**. | Only enumerated planning routes against isolated synthetic/non-sensitive development records; no role or membership needed. | No live send/publish/export/real approval/integration. |

The DB contract fixes the open-mode destination at the workspace-private `.local/open-development-planning/socket` Unix socket, PostgreSQL port 5432, database `open_development_planning`, and OS user. Open mode must **never consult `DATABASE_URL`**, even if it exists in the process environment. Isolation verification must inspect the actual connected server socket, data directory, database name and singleton marker (`synthetic-open-development-v1`), not rely on a claimed environment string. A failed, missing or invalid mode/isolation configuration must fail closed, never silently become open. Restricted mode uses the normal `DATABASE_URL` pool, but must reject a database bearing the development marker, even if a trusted principal is injected. Do not reuse a shared/operational database, import customer data or migrate shared/production. A private cluster initialization must be non-destructive and idempotent: never reset existing databases; only migrate/seed this newly isolated development cluster. Operators must inspect the active mode from the server's `GET /api/development/status` response; `planningAccess: true` does **not** imply operational authority. The application URL is supplied by the running artifact, not by this document; record the exact observed URL and active mode in the final report rather than inventing one.

Configuration is `PLANNING_ACCESS_MODE=restricted` (or unset) for restricted mode and explicitly `PLANNING_ACCESS_MODE=open-development` for isolated development only. `.replit` currently sets development-only `NODE_ENV=development` and `PLANNING_ACCESS_MODE=open-development` under `[userenv.development]`; these are **not** deployment values. The API artifact's `dev` command invokes `lib/db/scripts/open-development-planning.mjs dev`; `setup` initializes/verifies only the private development cluster without starting the API, `stop` stops that local PostgreSQL process without deleting plans, and `--help` displays launcher instructions. Do not run `setup` against pre-existing unknown directories: the launcher refuses interrupted or mismatched bootstraps rather than resetting them, and its existing-cluster migration manifest must match. `dev` in restricted mode does not provision the development cluster. The server itself requires `NODE_ENV=development` and a non-deployed environment to enable open mode, and calls `assertPlanningDatabaseIsolation()` before listening; `createApp` cannot be made open by a client hint. The browser must use same-origin `/api` calls. A verified private environment, not just an environment variable, is the prerequisite. This documentation does not start either workflow.

Synthetic prerequisites are a team (`00000000-0000-4000-8000-000000000001`), group (`...0002`), unverified creator (`...0003`) and distinct accountable owner (`...0004`). Synthetic users are **not** administrators or verified members and receive no roles or grants. The development environment marker and `development_record_registry` distinguish new development campaigns/activities from historical records; ownership is attached transactionally at creation, with stable record IDs. Default activity group inherits its campaign's current group; planning ownership can later change explicitly. Do not backfill historic ownership, infer it from `created_by`, or treat seeded Foundation taxonomy as verified. Production-mode checks must reject development-registry records as defense in depth.

The API contract exposes `GET /api/development/status` publicly in both modes with `{mode,planningAccess,unverified:true,operationalActionsEnabled:false}`. All other `/api/development/*` endpoints are restricted-denied: group listing/creation, campaign/activity ownership read/update, deduped activity calendar optionally filtered by group, and dry-run simulations are open-mode-only. `POST /api/development/simulations` is non-persistent and returns `simulation:true`, `unverified:true`, `authoritative:false`, `operationalReadiness:false`. Browser-origin mutations require a matching origin and request host; use same-origin requests, never query/header-supplied mode or claimed role. A visible open-development indicator and unverified markings must remain in the UI; a neutral unavailable notice in restricted mode is appropriate without trusted authentication.

For every O row, deny requests referring to historical/unregistered campaigns or activities, including nested IDs; aggregate responses must filter *before* counts and pagination. Block non-browser callers from evading operational restrictions too. Block unknown HTTP methods and paths. Do not expose production adapter status, secrets, unrestricted SQL or infrastructure management through this API. A permitted draft path can still reject invalid, destructive or finality-seeking input. `GET /api/development/groups`, `POST /api/development/groups`, `GET,PUT /api/development/ownership/:type/:id`, `GET /api/development/calendar`, and `POST /api/development/simulations` are additional **O** routes only; all are **R-denied** in restricted mode. Calendar entries are deduplicated by stable activity ID and contain planning summaries only, not evidence, notes, participants or budgets.

## Six-step restricted transition (no automatic promotion)

1. **Configure trusted authentication.** Select and verify a real issuer; bind its issuer/subject to actual staff identities and require verification in server composition. Disable open mode by explicit server configuration; absent/invalid configuration remains restricted or fails startup. No browser identity hints.
2. **Provision verified administrators, memberships and scoped roles.** Bootstrap with independently verified approver and audited out-of-band evidence; no self-elevation, fake administrator or unverified development identity. Verify revocation and job reauthorization.
3. **Review group ownership and collaboration grants.** Validate accountable owners, destination acceptance and child-group scopes, unresolved historical mappings and grants. Do not derive ownership from creator; do not expose historical records by switching modes.
4. **Separate development records from operational records.** Quarantine or review each candidate for promotion with fresh governed provenance; development-registry records and synthetic Foundation remain non-authoritative. No automatic data/approval copying or shared database migration. Preserve original legacy payload and evidence.
5. **Invalidate development sessions.** Revoke labels, caches and any development tokens; unverified creator/session attribution and simulated approvals/integration responses remain inadmissible operational evidence. Recheck stored plans and queued jobs without relying on former sessions.
6. **Enable restricted mode and verify boundaries.** Start against an approved non-development datastore only after isolation checks and trusted verifier; test unauthenticated deny, child/sibling scope, revocation, historical containment, export/live denial, readiness provenance and no automatic promotion. Any promoted plan must undergo normal validation, governed provenance and actual independent approvals. Stop rollout on any unexpected exposure.

**Preservation is not availability or authorization.** The additive organizational migration preserves original records and established webinar evidence; the original HTTP handlers were intentionally unmounted by the foundation. Open mode permits only separately isolated development records, not restoration of unrestricted legacy HTTP access. Neither preserved rows nor passing synthetic migration tests prove live workflow compatibility. The original Phase 2B-1 webinar increments, trusted restricted identity integration, safe legacy compatibility and live deployment remain pending.
