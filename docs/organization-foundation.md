# Organizational foundation — bounded Phase 2B-1 architecture

Authority: [Phase 2B-1 organizational owner decisions](verification/phase-2b-1-owner-decisions.md), [Phase 2B-0B assessment](verification/phase-2b-0b-group-hierarchy-impact-and-plan.md), [Phase 2B-0A decisions](verification/phase-2b-0a-acceptance-and-owner-decisions.md), and Phase 2B-0 section 16. This document describes the current bounded implementation and its activation prerequisites, **not an operationally enabled workspace**.

## Model and isolation

Migration `lib/db/migrations/0022_organizational_foundation.sql` adds side associations, leaving existing campaign, activity, webinar, communications, budgets and governed codes in their original stores. `organization_units` holds root `team` and child `group` IDs; groups require a parent team and accountable owner. A workspace is a logical group scope, not another store. Memberships reference existing `users.id` with verifier and revocation; grants reference a membership or recipient group and exactly one unit, campaign or activity scope. Six role values and five narrower action values are constrained. Parentage does **not** confer child access. One effective campaign/activity ownership row per mapped record is keyed by the existing record ID; campaign participation permits separately owned activities, but does not grant read access. Keep creator attribution, accountable person, owner group and collaborators separate. Append-only `organization_audit` and transfer acceptance rows record decisions. The service handles transaction-serialized changes; direct DB writers must be limited to trusted migration/bootstrap operators, not arbitrary application clients.

`legacy_campaigns` and `legacy_activities` snapshot pre-0022 identities as immutable cutoff registries. No creator-text inference or universal default assignment is performed. Existing unresolved records have no organizational ownership row and are excluded from new scoped summaries. Their preexisting payload, template version, planning and evidence remain untouched by 0022. **Their old HTTP handling is not currently reachable from the default app**: unscoped legacy routers are unmounted, rather than left as a bypass. This is an availability limitation, not a claim that historical payload has been migrated or that a replacement legacy HTTP workflow exists. Active `legacy_9` and `default_5` sessions must remain unchanged through completion; defer a historical association if it would change their behavior/evidence.

`artifacts/api-server/src/lib/organization/policy.ts` defines action checks; `service.ts` reloads membership/grant/ownership facts inside serialized transactions. A membership in B never imports an A-scoped role. Calendar viewing requires a specific group scope, summary visibility flag and fresh authorization. Participation alone conveys no access; reassessment flags limit post-transfer exposure: archived/unstaffed group records do not become visible through broad unit grants, and specifically authorized historical record access remains distinct. Transfer completion checks the ownership revision recorded at request time and cancels competing pending/accepted requests; stale transfers cannot silently succeed. Authorization for queued work must be checked again at execution and at delivery; stale session claims are never a durable grant. The serialized service lock is not a substitute for external authentication or authorization of direct SQL writers. Existing readiness, Foundation provenance, exception separation, non-overridable rules, release fingerprints, 106 canonical evaluator IDs, request-local diagnostics and no-send pilot restrictions still apply.

## Permission matrix

All rows require a trusted verified actor, active membership and explicit applicable group/record grant; the table is **action eligibility**, not implicit visibility. Record scope and canonical readiness/evidence checks are additional requirements.

| Role / grant | Read detail | Plan / evidence | Exceptions | Calendar summary | Administration | Financial / participants / execution |
|---|---|---|---|---|---|---|
| Planner | Scoped | Plan, submit evidence | No approval | Only if separately granted/visible | No | No |
| Exception Requester | Scoped | No | Request only; never approve own request across any group/role | Only if separately granted/visible | No | No |
| Independent Reviewer | Scoped | No | Review eligible evidence/exceptions; separate verified requester | Only if separately granted/visible | No | No |
| Operations Executor | Scoped | No | No | Only if separately granted/visible | No | Execution disabled in this pilot |
| Administrator | Not by role alone | No | No override | Only if separately granted/visible | Scoped membership, grant, group operations | No |
| Read-only Viewer | Scoped | No | No | Scoped visible summary | No | No |
| Explicit record collaboration action | `record_view` only | `record_edit` or `evidence_submit` only | No | No implicit calendar | No | No |
| Explicit `calendar_view` | No detail | No | No | Named child group only, activity explicitly marked summary | No | No |
| Explicit `financial_view` | No automatic detail | No | No | No | No | Separate financial permission; dashboard/rollup deferred |

The service has a calendar summary projection over existing `activities` plus `webinar_sessions` dates, deduped by activity identity in its activity iteration; it includes title, owning group/person, type, status and available occurrence-local date/time/zone. This is **not** a full master calendar: no visual UI, no generalized dated source adapter for non-webinar text timing, no approved/live status inference, no financial rollup, and no cross-resource totals or exports. Dates absent from typed sources are unavailable, not zero or invented instants. `calendarSummary` is service-only; there is no HTTP calendar endpoint. Calendar permission cannot open detail, participant data, notes, budgets, evidence or approvals.

## HTTP boundary and authentication dependency

`createApp()` mounts `/api` health and the organizational router, not the former global campaigns, portfolio, conflicts, search/export or mutation routers. It offers only `GET /api/organization/campaigns` and `GET /api/organization/campaigns/:id` as restricted campaign summaries; other organizational paths return 403 after authentication. The detail response is a campaign-only projection, not its activity/attachment graph. The middleware accepts a verifier injected by trusted **server composition**, not HTTP actor claims. No live verifier is wired into default `createApp()`, so ordinary non-health requests currently receive **503 `AUTHENTICATION_UNAVAILABLE`**. The frontend displays a neutral “Protected access is unavailable” notice rather than opening legacy product screens. The tests' injected verifier is a test harness, not operational authentication. Merely supplying a `VerifiedPrincipal` object with `issuer`, `subject` and `userId` to service calls does **not** prove the issuer/subject-to-staff-user binding: a real external authority must verify that relationship before exposure. Do not enable legacy routers as a fallback. Scope all affected direct/list/search/export/background paths before any re-enable, filtering before counts/pagination metadata; unresolved historical handling needs a separately safe authenticated compatibility route.

## Controlled provisioning / bootstrap (not an exposed setup API)

1. Keep the app's no-verifier 503 default and old routers unmounted. Obtain approved identity authority, uniquely bind authenticated issuer/subject to existing staff `users.id`, and verify staff roster and accountable ownership through authoritative out-of-band evidence. Never use email, free-text `users.role`, webinar participants or caller-supplied headers as proof.
2. In a restricted environment with trusted DB/service access, designate **two distinct verified people**: initial administrator and independent approver. Record evidence and approval outside the application before invoking `bootstrapTeam(actor, approver, {name,evidence})` once; the service rejects self-bootstrap and a second team. No public bootstrap endpoint exists. Treat this as a controlled capability requiring a privileged caller, not a self-service identity verifier.
3. Using independently verified parent-scoped Administrator authority, provision child groups with real accountable owners and reviewed rosters through `createGroup`; create/verify memberships and scope-specific grants via audited service operations. No group lead acquires administration merely through leadership. Confirm grants target explicit child IDs; adding/reparenting a child does not extend old grants automatically.
4. Map historical IDs only with reviewed evidence and audit (`mapHistoricalOwnership`); inventory unresolved/conflicting IDs first. Do not alter active legacy session evidence or silently force assignment. New creation must use a trusted transactional `assignOwnership` callback writing the record and owner together. Current old creation HTTP paths are disabled.
5. Before operational enablement, verify identity binding, least-privilege SQL access, complete affected-route containment, revocation at job execution/delivery, positive/negative scope tests, and unchanged legacy behavior. Without these dependencies, leave access disabled. No live exception approval, send/publish, or Foundation bypass is authorized.

## Migration, compatibility and recovery

`0022` is additive after `0001`–`0021`; it snapshots legacy IDs at the cutoff and adds tables, FKs, checks, partial active uniqueness, hierarchy/group validation and immutable cutoff/audit triggers. It does **not** backfill ownership or force NOT NULL group IDs onto historical campaign/activity tables. New-model ownership must be inserted in the same transaction as newly created records at the service boundary; SQL writers outside this boundary must be denied or separately controlled. The schema alone does not make existing inserts impossible, so do not enable bypass writes. No migration is applied to a shared/production database by this increment.

Rehearse fresh and synthetic prior-schema upgrades in isolated disposable databases, snapshot original rows before 0022 and compare after, including active legacy templates. If an upgrade fails, stop promotion, retain the original data and investigate the failing constraint; do not drop rows to make it pass. For a completed additive upgrade, prefer disabling new scoped exposure and a reviewed forward/compensating migration over destructive table rollback; keep original records and audit/evidence. Revoke mistaken access through audited service changes and restore verified ownership through reviewed compensating records rather than rewriting history. Revalidate affected grants, ownership/readiness and pending jobs before re-enabling; rollback must never remount unguarded global HTTP routes. Preserve approved retention and legal holds.

Remaining original Phase 2B-1 increments and activation conditions are tracked in [the bounded verification record](verification/phase-2b-1-organizational-foundation.md). This foundation does not certify full Phase 2B-1 completion.
