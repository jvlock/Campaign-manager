## 2. Current route, schema, error and security conventions (before implementation)

`artifacts/api-server/src/app.ts` mounts `/api` health and, in open-development mode, verifies isolated planning DB access before `developmentPolicy`, `developmentRouter`, and `planningRouter` (`routes/index.ts`, which mounts `routes/webinars.ts`). Restricted mode instead mounts only the organizational router behind `organizationAuthentication`; absent trusted authentication yields 503. Open-development's method/path allowlist, same-origin mutation check and `X-Planning-Attribution: unverified-development` are **not authenticated identity or scoped authorization**. Existing generated route links in `lib/api-spec/openapi.yaml` use `/api` as server base and unversioned resource paths; OpenAPI is **3.1.0**, document `info.version: 0.1.0`, generated React and Zod clients. There is no observed path/header API v1 version negotiation: standard ID/version, snapshot schema/release identity and OpenAPI contract version are separate concepts.

Validation is mixed: `routes/development.ts` uses strict Zod scope/body schemas for simulations and synthetic participant actions; `routes/development-foundation.ts` uses strict scoped GET/refresh schemas; legacy `routes/webinars.ts` validates UUID path params and domain inputs but some `z.object(...)` usage is not strict. Express JSON parsing has no explicit project-specific body-size setting observed at preflight. Responses are usually bare domain objects or arrays, with `simulation:true`, `operationalReadiness:false`, `unverified:true`, `authoritative:false` on development simulation outputs; there is **no consistent versioned envelope** for all routes. Errors are likewise mixed: legacy webinar validation often `{error: string}`, `ActivityModelError` `{error:{field,code,message}}`, development conflicts `{error: message,code,expectedRevision,currentRevision}`, policy denial `{error:{code,message}}`, and unexpected development failure a safe generic 503. The new contract should define stable codes narrowly without claiming that existing legacy routes already implement the proposed catalog. Never expose raw provider credentials, stack traces or identity claims.

`WebinarPersistence.withEvaluationTransaction` uses an occurrence advisory lock and revision check; `append` stores an immutable request hash plus occurrence-scoped idempotency key, a typed 0024 JSONB record, and a same-transaction actor audit row (attribution remains unverified). `simulateWebinarOccurrence` invokes the sole 106-rule orchestrator and immutable release/readiness snapshot. `transitionParticipantLifecycle` writes 0025 immutable source events, projected state, future obligations and linked snapshots transactionally; `createSyntheticParticipant` uses closed fixture identity. `resolveFoundationObservations` validates synthetic requests/responses, retries only bounded transient failures, reuses version/validity/release-matched immutable history, and `refreshFoundationObservations` invokes orchestration, not a standalone observation write. `captureWebinarRelease` hashes canonical documents, evaluator implementation and registry, installed dependency versions and Git HEAD but the **existing release digest also includes calculation time**; a later additive engine-release identity must separate engine release from evaluation context without changing historical digest semantics. Do not relabel or backfill prior snapshots.

OpenAPI additionally reserves `UNAUTHENTICATED` for a future trusted auth boundary, **not an achieved identity/login flow**. New route shape `{error:{code,message}}` never emits raw provider credentials or stacks. Provider classifier maps its 17 actual failure categories to the appropriate stable codes. An HTTP success does not make an unsupported governed output available.

Existing Foundation route errors are top-level `{error:string,code}` for handled validation/not-found/provider-not-configured/conflict, not the new router's envelope. No naming, code, UTM, objective, exclusion or external-production availability is inferred from a configured synthetic fixture.

**Additive release identity:** `engineReleaseIdentity` produces an `engineReleaseFingerprint` and `engineRelease` containing standard exact ID/version, five canonical hashes, evaluator-source/registry hashes and 106/106 coverage, application commit **or null if trustworthy build identity cannot be read**, and installed versions including Temporal.
