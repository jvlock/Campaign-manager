## Implemented orchestration and result contract — verified bounded development flow

`webinar-evaluation-sources.ts` reads campaign/activity/occurrence-scoped application and sidecar records with a **single-statement MVCC** query, requires registry-marked synthetic campaign/activity, explicit `new-synthetic-occurrence` plan and exact binding; `webinar-evaluation-orchestration.ts` calls the adapters, loads the validated catalog and checks exact catalog/registry/entry/invocation/result inventories against **106 unique canonical IDs**. It evaluates in deterministic dependency order, then invokes existing readiness and completion modules with **partial evidence and unknown operational obligations**. It persists only after successful validation and final source check. Missing canonical source facts remain explicit; an invalid or missing event-status input yields an unassessed/missing-evidence projection rather than a favorable result. Valid-context evaluator throws/invalid identities or coverage drift raise `EvaluationImplementationError` (503 through the development error boundary) **without a snapshot**; unavailable required input remains distinct from evaluator failure. Full population processing is **not claimed**: no participant population is loaded into this flow, and absence is reported, not treated as complete. Synthetic registry and occurrence scope do not imply authenticated group membership or operational authorization; existing development calendar pagination and source guards are bounded separately.

`webinar-simulation-snapshot.ts` strictly validates the internal result: Activity/occurrence, exact standard/version, fixed instant, release/input fingerprints, source references, all finding envelopes, applicable/passed rules, original unresolved and separately exception-resolved blockers, nonblocking failures/warnings, missing inputs, unavailable external observations, mapping errors, coverage, readiness stages/issues, completion projection and **`simulation-only`** status. `simulateWebinarOccurrence` adds snapshot ID/revision and **request-local** invoked-ID/error/replay/source-count diagnostics only on the response, not in the stored authoritative payload. A zero-blocker simulation is not operational readiness.

Foundation-dependent rule handling: `assembly.ts` reports unavailable governed objective (**WEB-SETUP-003**) and exclusion (**WEB-REC-010**) observation inputs separately; also reports absent local naming/code/taxonomy authority. Valid explicitly supplied **test-environment** Foundation observations may be consumed after scope/provenance checks; no connector is created, no free text substitutes. Implemented evaluator, present observation, connected live source are different claims; readiness effect is reflected in canonical findings, not bypassed by an invented observation. Sidecar exception-disposition metadata is intentionally reconstructed as incomplete/unverified by the orchestrator so an `approved` token alone cannot resolve a blocker. Original finding and canonical exception eligibility remain authoritative. Development actor IDs are attribution, not authentication.

Snapshot/fingerprint implementation: server-captured release digest from canonical hashes/runtime registry/dependency versions (`webinar-release-provenance.ts`); input hash over scoped source facts and fixed instant (`sourceInputFingerprint` omits non-domain canvas position, row audit counters and prior snapshots, while a separate full-source read token detects concurrent changes). `webinar-persistence.ts` now accepts optional **strict `simulationSnapshotSchema`** in readiness/completion payloads and checks occurrence, standard, calculation instant, input fingerprint, result hash and release digest against the immutable release record. The orchestrator appends a release and full readiness simulation in one occurrence transaction; source references, gaps, nonblocking and original findings reside in `webinar_persistence_records.payload` JSONB under existing `0024` (`lib/db/migrations/0024_webinar_persistence_foundation.sql`). This is a **code finding, not a database-gate result**: no DDL or `0025`. Equivalent same-key retry replays the prior row only for matching source/release/time/actor; changed input creates a different fingerprint/snapshot only under a fresh revision/key. Request diagnostics remain outside persisted simulation.

Concurrency implementation: `WebinarPersistence.withEvaluationTransaction` uses an occurrence-scoped advisory transaction lock and expected revision; `webinar-evaluation-sources.ts` takes short finalization **SHARE table locks** and re-reads the scoped source snapshot, comparing the full source read token before append/replay to reject modifications/phantoms. Same occurrence serializes; different occurrences can share finalization locks. Stale revision/source/release and altered retries conflict; final database/API gates and browser same-tuple replay/new-calculation scenarios passed as reported below. Synthetic creation uses explicit `developmentSimulation.eventStatus` opt-in, only for a new Webinar activity in open development (`routes/campaigns.ts`, `webinar-standard.ts`); `initializeNewSyntheticOccurrence` verifies the session was inserted **in the current transaction** (`xmin`), synthetic registry, and absence of legacy markers, then atomically appends exact binding plus simulation plan status. No existing `default_5`/`legacy_9` session is silently converted. The simulation loader excludes legacy sessions and requires the explicit new-synthetic plan. Existing `WebinarPersistence.load` revision pagination does not establish participant whole-population processing, which is not connected here.

Development surface: `GET /development/simulations/context` performs a fixed campaign/Activity/occurrence synthetic eligibility and exact-version/revision preflight; `POST /development/simulations` requires the same tuple plus fixed calculation instant, retry key and expected revision, then returns the structured simulation. Non-webinar requests remain a **generic preview, not a standards-engine result** (`routes/development.ts`, API specification/generated types). `Development.tsx` selects campaign → Webinar Activity → occurrence; preserves a fixed tuple for same-calculation retry and explicitly fetches new revision to start another calculation. It labels results **“Development simulation—nonoperational”** and separates blockers, warnings, gaps and unavailable observations. The new `developmentSimulation` creation opt-in is surfaced in the webinar setup flow and was confirmed by the browser verifier. No public operational approval/sending API is claimed.
