# Governed receipt clocks in immutable simulation replay

When validating an external-looking governed observation in development, three instants have different meanings: the caller's fixed evaluation `calculationAt` (as-of), the original transport `receivedAt` stored with the immutable receipt, and **current time** when history is reused. Do not conflate them. A response may legitimately be emitted and received *after* the fixed as-of calculation time; rejecting `respondedAt > calculationAt` wrongly rejects a valid transport. Conversely, comparing a historical `respondedAt` only to wall-clock time or replacing the stored receipt timestamp with a newly generated one on replay loses the original request's attribution and can make expired evidence appear current.

Validate on first receipt that `respondedAt` is not unreasonably later than actual transport receipt, and that the fixed as-of and original receipt are inside the claimed validity interval. Persist the original receipt timestamp separately from the provider's `respondedAt` and from `validFrom`/`expiresAt`. On history reuse, revalidate the original receipt with the **same as-of** and original receipt clock, then independently reject evidence expired at current time; retain original response, fingerprint, service/taxonomy/release versions and provenance. For GET inspection reconstruct the latest snapshot's fixed as-of/release digest rather than using a new digest every request. An identical retry must preserve input/release identity, not silently append or revise history. Explicitly distinguish a configured fixture, a provider validated **on this request**, a reusable historical observation and any actual live Foundation connection.

This boundary was exposed by more than one unsuccessful timestamp/replay approach in Phase 2B-4 before final deterministic and browser gates passed. It is a reusable time-and-provenance rule, not evidence that a synthetic fixture is a real Foundation endpoint or that operational readiness was approved.
