Phase 2B-3 should be accepted as complete for its synthetic-only scope. The participant lifecycle now has the necessary structural separation: event state, registration, attendance, communications and suppression are not being collapsed into one status.

The next increment is Phase 2B-4: integrate governed taxonomy, naming, campaign codes and UTM observations from the Governance Foundation. This must remain server-side and fail closed when authoritative output is unavailable.

# Phase 2B-4 — Governance Foundation Observation Integration

Integrate Governance Foundation outputs into the Campaign Manager webinar orchestration as authoritative governed observations.

The Foundation remains authoritative for:

* taxonomy;
* standardized internal naming;
* campaign codes;
* UTM generation;
* applicable governed classifications.

This increment must not duplicate Foundation logic locally, permit manual bypasses, add live sending, publish campaigns, process customer data, or deploy to production.

## 2. Preflight the actual Foundation capability

Before building a connector, inventory the Foundation implementation.

Determine:

* authoritative repository or service;
* available endpoints or internal service contracts;
* request and response schemas;
* authentication requirements;
* environment separation;
* taxonomy versioning;
* naming ruleset versioning;

Do not infer that a working user interface means a stable integration API exists.

If no versioned service contract exists, implement the Campaign Manager provider interface and a synthetic contract adapter, but do not invent or claim a live Foundation connection.

## 3. Required integration states

The system must distinguish these states explicitly:

| State                      | Meaning                                                      |
| -------------------------- | ------------------------------------------------------------ |
| Evaluator implemented      | Campaign Manager contains the applicable standards evaluator |
| Observation available      | A valid, versioned governed result has been supplied         |
| Connector configured       | A Foundation provider is configured for this environment     |
| Connector reachable        | The provider successfully responded                          |
| Live production connection | An approved production service and identity are connected    |

Do not collapse these states into a single “connected” or “ready” indicator.

Open-development mode may reach only an approved synthetic or nonproduction Foundation environment.

Do not connect to production Foundation data or services in this increment without explicit authorization.

## 4. Provider interface

Create one internal server-side `GovernanceFoundationProvider` interface or equivalent.

It must support governed requests for:

* taxonomy classification;
* standardized internal title;
* campaign code;
* UTM output;
* any other Foundation observation explicitly required by canonical webinar rules.

The provider interface must return:

* observation type;
* governed output;
* Foundation service identifier;
* exact service or ruleset version;
* effective taxonomy version;
* request or transaction reference;
* normalized input fingerprint;
* response timestamp;
* validity status;
* valid-from and expiration, where applicable;
* deprecation status;
* provenance;
* warnings;
* structured errors.

Requirements:

* no Foundation requests from browser components;
* no secrets in frontend bundles;
* no evaluator-specific network calls;
* no direct Foundation calls from UI routes;
* no locally generated substitute presented as Foundation output;
* no free-text override of a missing governed result;
* exhaustive handling of response status.

## 5. Canonical request construction

Create deterministic request builders from existing Campaign Manager source records.

At minimum, construct inputs for:

* campaign identity;
* webinar activity;
* occurrence;
* product family or governed product selection;
* audience;
* geography;
* industry;
* channel;
* activity type;
* communication type;
* destination;
* content or asset reference;
* language;
* dates required by naming or code generation;
* existing stable identifiers.

Requirements:

* include only data required by the Foundation contract;
* use stable identifiers where available;
* normalize values deterministically;
* preserve missing versus empty versus not applicable;
* do not infer governed taxonomy values from display labels;
* do not send customer or participant data;
* calculate the input fingerprint before provider invocation;
* identical normalized inputs must produce the same fingerprint;
* changed governed inputs must produce a different fingerprint.

## 6. Governed observation validation

Treat every provider response as untrusted until validated.

Validate:

* response schema;
* observation type;
* request reference;
* input fingerprint;
* service version;
* taxonomy version;
* activity and communication scope;
* response timestamp;
* validity window;
* deprecation status;
* required provenance;
* output completeness;
* absence of unknown or prohibited fields.

Reject or mark unavailable any response that is:

* malformed;
* incomplete;
* for a different input fingerprint;
* for another activity or occurrence;
* expired;
* from an unsupported version;
* from a prohibited environment;
* missing provenance;
* internally inconsistent;
* partially successful where a complete atomic result is required.

Do not repair malformed governed output locally.

## 7. Observation persistence

Use the Phase 2B-1 governed-observation persistence foundation.

Persist each accepted observation as immutable history containing:

* activity and occurrence scope;
* communication or deliverable scope where applicable;
* normalized input fingerprint;
* governed result;
* exact Foundation versions;
* request reference;
* provenance;
* validity information;
* received timestamp;
* supersession relationship;
* Campaign Manager release fingerprint;
* environment classification;
* simulation-only status where applicable.

Requirements:

* do not overwrite historical observations;
* a new observation supersedes rather than silently replaces the prior record;
* retries with the same request and result remain idempotent;
* conflicting results for identical inputs must be surfaced;
* expired or deprecated observations remain auditable but cannot satisfy current readiness;
* source facts remain separate from governed observations;
* governed observations remain separate from evaluation results.

## 8. Cache behavior

If local caching is appropriate, the cache must not become the authoritative source.

Cache keys must include:

* observation type;
* input fingerprint;
* Foundation service version;
* effective taxonomy version;
* environment.

Requirements:

* respect Foundation validity and expiration;
* invalidate when governed input changes;
* invalidate when the required version changes;
* never treat stale output as current;
* show when a cached observation is used;
* preserve original provenance;
* do not serve production observations in open-development mode;
* do not permit cache fallback when the canonical rule requires a fresh result;
* distinguish unavailable, stale, expired and deprecated.

Document the cache decision even if no cache is implemented.

## 9. Failure behavior

Foundation-dependent evaluation must fail closed.

Handle separately:

* provider not configured;
* provider unreachable;
* timeout;
* authentication failure;
* authorization failure;
* rate limiting;
* invalid request;
* malformed response;
* fingerprint mismatch;
* unsupported version;
* deprecated version;
* expired observation;
* partial response;
* conflicting response;
* internal provider failure.

Expected behavior:

* draft planning may continue;
* non-Foundation evaluation may continue;
* the missing governed observation remains visible;
* affected rules show the correct incomplete or blocked result;
* operational readiness cannot be established;
* no local substitute is generated;
* retries follow bounded provider guidance;
* failure diagnostics do not expose secrets;
* users receive a clear, actionable development message.

Do not convert an outage into a valid empty observation.

## 10. Retry and idempotency

Implement bounded, safe retry behavior.

Requirements:

* reuse the same idempotency or request reference for a retry of the same logical request where the Foundation contract supports it;
* do not retry validation errors;
* do not retry authentication or authorization failures blindly;
* honor provider rate-limit guidance;
* use bounded backoff for transient failures;
* avoid duplicate persisted observations;
* record retry count and final disposition;
* protect against concurrent duplicate requests;
* do not introduce an unbounded background retry process.

## 11. Orchestration integration

Integrate governed observations through the single Phase 2B-2 orchestration boundary.

Required sequence:

1. Load source records.
2. Assemble normalized governed inputs.
3. Resolve a valid existing observation or invoke the configured provider.
4. Validate the observation.
5. Persist it immutably.
6. Map it into canonical engine input.
7. Invoke applicable evaluators.
8. Calculate readiness and completion.
9. Persist a new immutable simulation snapshot.
10. Return request-local diagnostics.

Requirements:

* evaluators remain pure and do not call Foundation;
* routes and UI do not call individual evaluators;
* missing observations stay explicit;
* updated observations create new input fingerprints and snapshots where relevant;
* historical snapshots retain the exact Foundation versions used;
* a valid taxonomy result cannot substitute for missing naming, campaign-code or UTM output;
* each governed observation satisfies only its applicable rules.

## 12. Standardized naming

For standardized internal titles:

* consume only Foundation-governed output;
* preserve the human-readable title and required structured components;
* retain the exact ruleset version;
* prevent manual edits from being represented as governed output;
* permit a separately labelled planning draft if current product behavior requires it;
* show differences between a draft title and governed title;
* do not silently overwrite user-entered planning context;
* require regeneration when governed inputs change.

## 13. Campaign codes

For campaign codes:

* treat the Foundation-issued code as authoritative;
* enforce exact activity and campaign scope;
* preserve uniqueness and provenance;
* prevent local code generation from bypassing Foundation;
* treat code conflicts as errors requiring resolution;
* do not recycle historical codes;
* do not create a production code in a synthetic environment;
* clearly distinguish simulated or reserved development codes.

## 14. UTM output

For UTM generation:

* obtain the governed parameter set from Foundation;
* preserve exact casing, normalization and version;
* persist both structured parameters and the resulting governed URL or output;
* validate the destination before combining it with governed parameters;
* do not treat a manually assembled UTM as governed;
* ensure the output is scoped to the correct communication and destination;
* regenerate when governed inputs or destination change;
* retain prior versions for audit;
* never expose secrets or internal service credentials in URLs.

## 15. Taxonomy

For governed taxonomy:

* map Foundation identifiers to existing application references;
* preserve stable taxonomy identifiers, labels and version;
* do not use labels as durable keys;
* retain deprecated classifications for history;
* prevent deprecated values from satisfying current rules unless explicitly permitted;
* surface unmapped identifiers as errors;
* do not add Foundation taxonomy administration to Campaign Manager;
* do not import the full Foundation catalog unless the accepted contract requires it.

The Foundation remains the authoritative catalog owner.

## 16. Development UI

Add only the limited UI required to inspect governed observations in open development.

Show:

* observation type;
* governed output;
* available, unavailable, stale, expired or deprecated status;
* Foundation service version;
* taxonomy or ruleset version;
* request reference;
* input fingerprint;
* received and expiration timestamps;
* whether the result came from a configured synthetic provider or a cached observation;
* affected readiness rules;
* simulation-only status.

Provide a development action to request or refresh an observation only when a synthetic provider is configured.

Do not allow users to type a governed result manually.

Do not show “Foundation connected” unless a provider call has been successfully validated.

## 17. Security

* server-side provider calls only;
* secrets loaded through approved server configuration;
* no secrets in logs, snapshots, browser payloads or error messages;
* explicit environment allowlist;
* production endpoint blocked in open-development mode;
* synthetic endpoint blocked from being represented as production;
* TLS validation retained;
* bounded request size;
* response-size limit;
* timeout enforcement;
* audit provider invocations without storing unnecessary payloads;
* no customer or participant data sent to Foundation.

Missing or invalid security configuration must fail closed.
