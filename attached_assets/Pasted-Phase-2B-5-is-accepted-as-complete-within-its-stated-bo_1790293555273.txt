Phase 2B-6 — Webinar Setup and Recruitment UI

Implement the guided Setup and Recruitment user experience for webinar Activities using the accepted Phase 2B-5 API contracts.

This phase must turn the underlying webinar standard into a clear, visual workflow that tells users:

* What is happening.
* What information is needed.
* What has been completed.
* What needs attention.

* What the system recommends next.

The experience must be understandable without a training manual.

Do not build the Follow-up or full Readiness screens in this phase. Do not introduce external sending, publishing, customer-data processing, production Foundation connectivity, deployment, or operational approval.

3. Governing user-experience principles

The UI must follow these principles.

3.1 Clear without training

A user should immediately understand:

* Where they are.
* What they are creating.
* Their current step.
* What has already been completed.
* What the system needs next.
* Why information is required.
* What will happen after they continue.

Do not require users to read large blocks of instructional text.

3.2 Guided choices over open text

Use structured controls wherever the system has a governed or finite choice:

* Radio groups.
* Selectors.
* Searchable dropdowns.
* Date and time controls.
* Status choices.
* Reusable content or destination selectors.
* Checklists.
* Preset cadence options.
* Recommended defaults.

Use open text only when the answer is genuinely unstructured.

Never turn canonical enumerations into free-text fields.

3.3 Simple with depth

Show the minimum needed for the current decision while keeping detail accessible through:

* Expandable guidance.
* Tooltips.
* “Why this matters” explanations.
* Optional advanced settings.
* Evidence details.
* Rule findings.
* History drawers.

Do not display every rule, field, and diagnostic at once.

3.4 Visual hierarchy

Webinars should use the application’s approved webinar color family. If no approved activity-color system exists, use green as the provisional webinar family:

* Primary webinar activity: core green.
* Recruitment communications: progressively differentiated green shades.
* Informational states: neutral blue or established application token.
* Warnings: amber.
* Blocking issues: red.
* Completed items: success green with a distinct icon.
* Unavailable external capabilities: neutral gray.
* Synthetic or simulated capabilities: clearly labeled purple or another distinct non-production token.

Do not rely on color alone. Every state must also use text and an accessible icon.

3.5 Familiar icons

Use the existing icon library and familiar meanings:

* Calendar for date and time.
* Clock for cadence and deadlines.
* People for audience.
* Envelope for communications.
* Link for destination.
* Shield or check badge for governance.
* Warning triangle for issues.
* Lock for unavailable restricted actions.
* History for audit records.
* Sparkle or flask only for clearly identified simulation.
* Check circle for completed work.

Do not introduce decorative icons that make actions ambiguous.

3.6 Immediate status and next action

Every major screen must show:

* Overall step status.
* Completion percentage or completed-item count where meaningful.
* Highest-priority unresolved item.
* Recommended next action.
* Saved or unsaved state.
* Last evaluation time.
* Whether results may be stale.

3.7 Honest operational boundaries

The UI must never imply that:

* A synthetic result is live Foundation output.
* Planned communications have been sent.
* A configured provider is connected.
* A rule has passed because evidence was merely submitted.
* Evaluator coverage means the webinar is ready.
* An unauthenticated user is an authenticated reviewer.
* An exception has been approved when review is unavailable.
* A successful API call means external execution occurred.

6. Setup experience

Design Setup as a guided workflow organized around:

* Why
* Who
* What
* When
* Where
* How

Do not force those labels where another existing application term is more precise, but preserve the underlying logic.

6.1 Why — objective and purpose

Display:

* Webinar objective.
* Intended customer or business outcome.
* Campaign relationship.
* Optional Journey relationship.
* Measurement intent.

Requirements:

* Use governed objective choices when available.
* Because governed objective output is currently unavailable, show the correct unavailable state.
* Do not silently fall back to a synthetic or locally invented governed objective.
* If manual planning input is already authorized, label it “Planning input—not Foundation governed.”
* Explain what remains required before operational use.

6.2 Who — audience

Display and edit authorized audience-planning information:

* Audience or segment.
* Geography.
* Language.
* Participant or registration summary.
* Inclusion criteria.
* Exclusion requirements.
* Internal/test exclusion.
* Competitor or governed exclusions where applicable.
* Waitlist approach.

Requirements:

* Separate planned audience from actual registrants.
* Separate population summaries from individual customer records.
* Do not introduce customer-data processing.
* Because Foundation exclusions are unavailable, show that state explicitly.
* Do not allow manual input to masquerade as governed exclusion output.
* Clearly surface registration suppression behavior.

6.3 What — webinar and content

Display:

* Webinar title.
* Internal working title.
* Webinar type.
* Topic.
* Speakers or hosts where supported by the existing model.
* Description.
* Primary CTA.
* Supporting asset or deliverable.
* Landing-page or registration destination.
* Follow-up-content readiness summary.

Requirements:

* Reuse existing content, asset, destination, and deliverable selectors.
* Every communication requiring a destination must reference an existing destination or create a properly scoped draft through an already authorized workflow.
* Do not build a separate asset-management system.
* Do not generate customer-facing copy in this phase.
* Clearly distinguish internal planning titles from governed naming output.
* Governed standardized naming remains unavailable until Foundation supplies it.

6.4 When — occurrence and timing

Display and edit authorized scheduling facts:

* Event date.
* Start time.
* End time or duration.
* Time zone.
* Registration opening and closing times where supported.
* Recruitment-window status.
* Shortened-window warnings.
* Relevant deadlines.

Requirements:

* Use exact instants and the accepted Temporal implementation.
* Never infer time zone silently.
* Display a readable local time and the stored time zone.
* Warn before a date change that affects planned communications.
* Show which recruitment communications would become overdue or invalid.
* Do not schedule or send externally.

6.5 Where — delivery location

Display:

* Virtual, in-person, or hybrid status where supported.
* Webinar or venue provider.
* Registration destination.
* Join destination status.
* Provider-connection status.

Requirements:

* Distinguish configured from connected.
* Distinguish planned destinations from verified operational destinations.
* Do not claim ON24, MCA, Teams, or another provider is connected unless repository evidence proves it.
* Do not expose secrets or provider configuration details.

6.6 How — operating plan

Display:

* Recruitment cadence.
* Reminder plan summary.
* Follow-up obligation summary.
* Registration and suppression behavior.
* Evidence requirements.
* Governance status.
* Foundation-observation status.
* Readiness summary.

The system should explain what it will plan, not claim what it has executed.

7. Setup workflow behavior

The Setup workflow should use:

* A left-side or top-level stepper consistent with the existing responsive design.
* One primary decision area at a time.
* A persistent task/status panel on larger screens.
* A collapsible task drawer on smaller screens.
* Save-and-continue behavior.
* Back navigation that preserves valid work.
* Clear validation at field and section levels.
* A final Setup review page.

The Setup review must group findings into:

* Complete.
* Recommended improvements.
* Warnings.
* Blocking issues.
* Unavailable governed capabilities.
* Missing evidence.
* Stale results.

Allow the user to navigate directly from a finding to the relevant Setup section.

Do not use one long, undifferentiated form.

8. Recruitment experience

The Recruitment area must present communications as a visual sequence anchored to the webinar date.

8.1 Recruitment timeline

Show the approved recruitment communications visually, including the standard cadence where applicable:

* Approximately 21 days before.
* Approximately 14 days before.
* Approximately 7 days before.
* Approximately 1 day before.

The actual engine output remains authoritative. The UI must not hardcode these intervals in a way that overrides scheduling rules, shortened-window logic, applicability, or canonical requirements.

For each touch show:

* Touch name.
* Relative timing.
* Calculated scheduled instant.
* Status.
* Audience state.
* Registration-suppression behavior.
* Destination.
* Content or deliverable status.
* Evidence status.
* Warnings.
* Blocking issues.
* Whether the touch is planned, suppressed, overdue, cancelled, or historically executed.

Use progressively differentiated shades from the webinar color family.

8.2 Communication cards

Each communication card should use progressive disclosure.

Collapsed state:

* Name.
* Timing.
* Status.
* Primary issue.
* Destination status.
* CTA status.
* Registration-suppression status.

Expanded state:

* Subject or content reference where available.
* Audience and exclusions.
* Scheduled instant.
* Dependency information.
* Destination.
* Evidence.
* Rule findings.
* History.
* Edit action where authorized.

Do not display a send button.

8.3 Visual scheduling

Show:

* Webinar date as the timeline anchor.
* Past, current, and future communications.
* Overdue items.
* Shortened-window changes.
* Suppressed items.
* Cancelled items.
* Historical execution separately from future plans.

Do not use drag-and-drop if moving a card would violate calculated scheduling or imply unsanctioned execution.

If drag-and-drop already exists, restrict it to authorized planning adjustments and show the resulting rule impact before saving.

8.4 Registration suppression

Make registration suppression visible and understandable:

* “Registered participants are removed from future recruitment.”
* Suppressed communications remain visible.
* Suppression reason is shown.
* Historical executed communications remain visible.
* Cancellation does not silently restore recruitment eligibility.
* Internal/test records remain excluded.
* Governed exclusions cannot be bypassed.

Because no customer-data processing is authorized, use synthetic population summaries and existing test fixtures only.

* Planned touches.
* Complete plans.
* Missing destinations.
* Missing content references.
* Missing evidence.
* Suppressed touches.
* Overdue touches.
* Blocking findings.
* Nonblocking warnings.
* Readiness-to-recruit status.
* Last calculation time.
* Staleness status.

“Ready to recruit” must come from the engine. The UI must not calculate it independently.
