## 3. Architectural objective

Create one internal orchestration boundary that converts existing application records into the exact Phase 2A engine input contracts.

The required direction is:

```text
Existing application records
        ↓
Domain adapters
        ↓
Canonical evaluation input
        ↓
106-rule standards engine
        ↓
Evaluation and readiness results
        ↓
Immutable development snapshot
```

Requirements:

* Existing application records remain authoritative for application state.
* Phase 2A domain types remain authoritative for engine input.
* Adapters translate between the two.
* Adapters must not create a second webinar model.
* Evaluators must not query the database directly.
* Routes and UI must not recreate evaluation logic.
* Persistence services must not reinterpret rule semantics.
* A webinar remains an Activity, never a Journey.

## 5. Adapter requirements

Implement typed, testable adapters for the required existing application sources.

Each adapter must:

* accept explicit source records;
* return the exact canonical domain type;
* perform structural validation;
* preserve stable identifiers;
* preserve date, time-zone and occurrence semantics;
* distinguish missing from false, zero, empty and not applicable;
* return structured mapping errors;
* avoid database access inside pure mapping functions;
* avoid mutating source records;
* produce deterministic output;
* document every derivation;
* reject ambiguous mappings where the canonical meaning cannot be established.

Prefer small adapters grouped by domain responsibility rather than one large mapping function.

## 6. Preserve critical source boundaries

The adapters must preserve these distinctions:

* Campaign is separate from Activity.
* Webinar is an Activity.
* Webinar occurrence is separate from the webinar definition.
* Event status is separate from participant status.
* Attendance is recorded per registrant.
* Planned communication is separate from executed communication.
* Scheduled time is separate from actual execution time.
* Evidence is separate from an exception.
* A valid exception resolves only an eligible blocker.
* Development attribution is not verified identity.
* A simulation result is not operational readiness.
* Foundation-dependent observations are not locally recreated.
* Missing Foundation output remains unavailable.
* Unknown attendance is not treated as attended or absent.
* Neutral follow-up is a distinct variant.

Add regression tests for every boundary.

## 7. Evaluation input assembly

Create a deterministic input-assembly service that:

1. Loads the authorized occurrence-scoped application records.
2. Invokes the relevant adapters.
3. Validates the assembled canonical input.
4. Records all missing, invalid and unavailable inputs.
5. Invokes the existing evaluator registry.
6. Applies existing exception resolution.
7. Calculates readiness stages using the existing readiness module.
8. Calculates completion using the existing completion module.
9. Produces request-local diagnostics.
10. Creates an immutable simulation snapshot through the Phase 2B-1 persistence service.

The assembly service must not:

* change evaluator semantics;
* add rule-specific logic outside evaluators;
* infer external execution;
* manufacture evidence;
* manufacture Foundation observations;
* convert planning records into operational facts;
* treat evaluator coverage as readiness;
* hide nonblocking findings;
* suppress missing evaluator or input coverage;
* mutate application records.

## 8. Result contract

Return one structured internal result containing:

* activity and occurrence identifiers;
* standard identifier and exact version;
* calculation instant;
* release fingerprint;
* input fingerprint;
* source-record references;
* applicable rules;
* passed rules;
* unresolved blocking failures;
* blockers resolved by valid exceptions;
* nonblocking failures;
* warnings;
* missing input data;
* unavailable external observations;
* mapping errors;
* evaluator coverage;
* readiness-stage results;
* completion result;
* request-local diagnostics;
* snapshot identifier;
* explicit operational status.

For open development, operational status must always be:

`simulation-only`

A result with no blocking failures must still remain nonoperational when required authorization, governed observations, evidence or integrations are unavailable.

## 9. Foundation-dependent rules

Do not build the Foundation connector in this increment.

For rules dependent on taxonomy, standardized naming, campaign codes or UTM output:

* consume an existing valid governed observation if one is explicitly present;
* otherwise mark the governed observation unavailable;
* do not calculate a substitute locally;
* do not accept free-text or manual values as governed evidence;
* preserve provenance and version information;
* identify every affected rule;
* show the resulting readiness effect accurately.

Clearly distinguish:

* evaluator implemented;
* governed observation present;
* live Foundation connector connected.

Only the first is guaranteed in this increment.

## 10. Evidence and exception handling

Use the Phase 2B-1 persistence services.

Requirements:

* Evidence metadata may be mapped into canonical evidence inputs.
* Source content remains referenced rather than unnecessarily duplicated.
* Development evidence remains labelled unverified.
* Development exceptions are simulated only.
* A simulated exception cannot establish operational readiness.
* Exception eligibility remains controlled by canonical rule metadata.
* Non-overridable rules remain non-overridable.
* Self-approval remains prohibited in restricted mode.
* Open development does not fabricate an approver.
* Invalid, expired, denied, incomplete or mismatched exceptions do not resolve blockers.

Do not create operational evidence or approval APIs.

## 11. Attendance and participant handling

No customer or production participant data may be introduced.

Use synthetic records only.

The adapter must support the canonical distinctions among:

* registered;
* waitlisted;
* cancelled;
* attended;
* absent;
* attendance unknown;
* internal or test record;
* suppressed or excluded record.

Requirements:

* Attendance remains per registrant.
* Event status never substitutes for attendance.
* Unknown attendance remains unknown.
* Cancellation does not become absence.
* Internal and test records remain excluded where required.
* Neutral follow-up obligations remain distinct from attended and absent follow-up.
* Population processing must use the Phase 2B-1 deterministic pagination contract.

## 12. Scheduling and time handling

Preserve the existing Temporal-based scheduling contracts.

Requirements:

* use the exact pinned Temporal dependency;
* preserve event time zone;
* preserve calculation instant;
* distinguish local scheduled time from absolute instant;
* handle daylight-saving transitions;
* maintain deterministic ordering;
* do not use the server’s implicit local time zone;
* do not silently reschedule invalid or missed obligations;
* distinguish planned, due, overdue, suppressed, cancelled and executed states.

Add boundary tests for DST changes and cross-time-zone calculations.

## 13. Snapshot behavior

Development evaluation snapshots must:

* be occurrence-scoped;
* use the Phase 2B-1 release fingerprint;
* include an input fingerprint;
* be immutable;
* preserve source references;
* preserve missing and unavailable inputs;
* preserve original failures after exception resolution;
* preserve nonblocking findings;
* use idempotency to prevent duplicate equivalent snapshots;
* create a new snapshot when a relevant input changes;
* never overwrite historical results;
* remain labelled simulation-only.

Request-local diagnostics must not become authoritative snapshot evidence.

## 14. Concurrency

Verify the orchestrator under concurrent requests.

At minimum test:

* two evaluations of different occurrences;
* two concurrent evaluations of the same occurrence;
* input changed during evaluation;
* stale version conflict;
* duplicate retry with the same idempotency key;
* equivalent input producing deterministic fingerprints;
* changed input producing a new fingerprint and snapshot;
* no leakage of diagnostics between requests;
* no leakage of records between groups;
* complete paginated population processing.
